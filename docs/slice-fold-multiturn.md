## 条件对齐与环境体检

历史 default 臂在 web profile 宿主上跑:不注入 effort(适配器出厂档 = high)、每轮无步数顶、
完整工具栈(read/write/edit + grep/glob + bash)。本次 slice+折叠臂用 `run-scenario.mts`
`--effort inherit --max-steps 250 --tools full` 对齐这三点。每格账本记录**实际生效**的环境
(从请求头读 effort、注册表读工具清单):`resolved=high · maxStepsPerTurn=250 ·
tools=[read,write,edit,glob,grep,bash,recall_turn,recall_search,recall_step]`。

两次作废的教训:① 第一轮用产品默认(low、meta 的 12–14 步顶)跑,s1 第一轮就撞顶,与历史不可比;

(`this.ctx.subprocess.spawn is not a function`),s10 的"build id 丢失"就是脚本没跑成。之后加了
探针场景 `z0_env_smoke`(六种工具在两臂各真实执行一遍、verify 判定)作为每次批次前的体检。
作废账本存 `results/20260902-multiturn/{low-capped,bash-broken}/`。

## 多轮编码的重读税:实验(2026-09-03 下午,s2/s3,历史条件)

逐轮画像(transcript 用 8 月会话日志)显示 slice 在 s2/s3 上输在输出侧:每轮重读 2–3 个文件
(s2 读 26 次对 transcript 8 次)、重跑测试(22 对 13)、重新推导(推理 76K 对 35K)。四个配置:

| s2 任务图 | 步数 | 重读 | 推理 | 成本 | s3 | 成本 |
|---|---|---|---|---|---|---|
| A 现状 slice(存 patch) | 108 | 26 | 76K | $0.120 | | $0.081 |
| B + 只读文件轮末进磁带(`tape.readBases`) | 101 | 20 | 76K | $0.109 | | — |
| C + 索引写明"current in tape"、整读现行文件返回指针(`tape.readPointer`) | 66 | 5 | **126K** | $0.136 | | $0.085 |
| D + 锚定只存完整 base(`tape.anchor: 'base'`) | 62 | 5 | 72K | **$0.099** | | $0.082 |
| transcript(历史) | 68 | 8 | 35K | $0.081 | | $0.051 |

三个发现:① 磁带里有全文,模型照样重读——它不会自己对哈希(B 只少了 6 次读);② 一旦索引
写明"不必重读",模型改成在脑中把 base 加一串 patch 合成当前文件,推理翻倍(C),用 `sha256sum`
自查,最后用 `cat -n` 绕过指针;③ 完整基线(D)消掉了合成税:s2 −18%,s3 持平——剩下的差距是
每轮改过的文件重新落一份完整 base 的未命中(s2 91K 对 31K)与仍然两倍的推理。
**默认保持关闭**(`readBases`/`readPointer` false,`anchor` 'auto'),三个旋钮可选;s3 持平、
其余场景未验证,不足以改默认。账本:`results/20260903-{readbases,readptr,anchorbase}/`。

## 磁带内容与结构的第二轮(2026-09-03 晚;目标:成本最低、正确度不降;峰值不设约束)

从 D 出发。先把 D 的种子与每步用量拆开(sidecar 记录每轮编译后的 seed 与每步 usage):

- **成本构成(D,s2)**:输出 70%(推理 72K)、封存追加的 miss 17%、轮内 miss 4%、hit 10%。
- **结构浪费**:base 模式下同一轮内每次成功编辑各落一份完整基线,第 7 轮磁带上有 13 份
  `scheduler.py`,只有 1 份是当前版;封存 miss 75K token(patch 模式 32K)。
- **推理税全在每轮第 1 步**:slice 各配置首步推理 31–52K,transcript 两次 8K/24K(s2)、8K/14K(s3);
  首步之后两臂完全一样(各约 15K)。A 配置(存 patch)首步只有 18K,但后续步 57K——重读、重测、
  重推导;base 模式把这笔税从后续步搬到了首步(拿着完整文件先想清楚再直接落编辑)。C 配置
  (patch + "不必重读")首步 102K,就是在脑中合成 base+patch。
- **可见输出**(非推理部分)里 bash 占六成:模型在 bash 里写长 heredoc 探针(每次 2–3.5K 字符),
  历史 default 会话同样如此(每会话 16–20 个),是 effort high 下模型的固有习惯,slice 只是次数更多。

四个旋钮,各跑 s2/s3 一次(塌缩在 s2 复跑一次),历史条件:

字节;回复留全、测试结论、旧推理链都动不了它,下一步应当从"开轮更便宜"入手(更短的磁带规则、

## 第三轮:新默认的验证与"开轮更便宜"(2026-09-03 夜)

**磁带规则是不是通用的?** 用 `~/.dsh/sessions` 里 89 个历史 h2h 会话(20 余种任务形状、两个臂)离线核验,
不跑模型:被读过的 1349 个文件里 91% 只在一轮里被读过;"读一次就锚"要往磁带放 9977 KB,"再读才锚"
只放 296 KB(3%)。新建的 366 个文件只有 12% 在后续轮被再次碰到(按字节 0.2%)。这两条 rent-or-buy
规则(`readBasesMinReads: 2`、`newFileMinTouches: 2`)不预测任务,只看模型自己的访问记录,最坏多付
一次读;所以是通用的。不通用的部分:完整基线锚定只在 7K 字符的文件上测过(历史库里没有超过 60K
的文件,大文件保护从未触发);指针依赖模型听从提示;数据都来自一个模型、一个 effort 档。

**新默认在其余多轮场景**(历史条件,单次):

| 场景 | 新默认 | 旧 slice(A) | transcript / default |
|---|---|---|---|
| s1 长程调试 | ✓ **0.050** | ✓ 0.068 | 0.090 / 0.091 |
| s4 多文件重构 | ✓ 0.145 / 0.134(第二次带 GC) | ✓ 0.125 | 0.143 |
| s5 常驻约束 | ✓ 0.143 / 0.181(第二次带 GC;推理 128K / 171K 对 74K,重读 9 / 10 对 36) | ✓ 0.118 | — |
| s6 按引用回退 | ✓ 0.170 / 0.212(第二次带 GC;推理 146K / 172K 对 97K,重读 7 / 17 对 32) | ✓ 0.159 | — |

s1/s2 赢、s4/s5/s6 输(都是单次),六个编码场景总价 0.672 对 0.671,打平但符号随任务形状翻转。
多文件形状上的规律一致:重读降到零(36→9、32→7),每轮步数从 8–19 降到 3–9,推理却涨五到七成
(s5 74K→128K、s6 97K→146K)且分布在大多数轮——拿到整个工作集后模型改成"在脑中做",而旧 slice
是"用工具做";按 DeepSeek 价目,推理输出($0.66/M)比多走几步工具(命中价上下文 + 小输出)贵得多。
**种子大小不是原因**:241 个开轮样本(s1–s6 全部配置)里,种子字符数与首步推理 token 的相关系数
0.01,按种子分桶的中位数 3.0K–5.6K 没有单调关系;所以清理旧基线(GC)缩小种子不会减少推理,
它省的只是命中字节。历史库里的多轮会话工作集几乎都是 1–2 个文件(跨轮编辑过的文件 ≤ 2),
s4/s5/s6 这种 8–12 文件的形状历史上没有样本——它们是新默认真正没被调过的地方。

**开轮在想什么**(runner 现在把每步推理原文落进 `.full.jsonl`,`scripts/turnstart-share.py` 统计首步
推理里提到 tape/[base]/sha256/patch 的段落占比):s1 首步推理 109K 字符里 28% 在解读磁带——"[base] 怎么
已经包含上一轮的改动、patch 在哪";s2 18%、s3 7%、s4 8%。其余是任务本身的推敲(算法分支、README
条目位置、幽灵 bug 的反复自证),磁带内容改不动。三个针对"解读磁带"的确定性改动:

1. **头部跟着磁带内容走**:没有 patch 的磁带用快照语义的头部("[base] 是该轮轮末的完整文件,最新的
   [base] 就是你最后知道的版本,索引说 current in tape 就直接改"),不再讲 base+patch 合成。
2. **被取代的基线即时清理**(`tape.gcSupersededBases`,可选):封存时若改写代价 ≤ 新 base 字节就删掉旧
   base,种子里每文件只剩一份现行基线。s2 两次 0.080 / 0.113,s3 0.097(噪声内);种子峰值 51K 对 88–109K,
   命中字节少四成,再没触发过整带折叠。
3. **摘要头不再打印 `task unknown`**。

| s2(历史条件) | 成本 | 首步推理 | 解读磁带占比 |
|---|---|---|---|
| 新默认(塌缩,旧头部)×3 | 0.077 / 0.077 / 0.112 | 38–49K | — |
| + GC ×2 | 0.080 / 0.113 | 40K / 61K | 18% / 14% |
| + GC + 快照头部 ×2 | 0.103 / 0.085 | 63K / 57K | 8% / 10% |
| + GC + 快照头部 + 新建文件再碰才锚 ×2 | 0.100 / 0.066(两次都没写探针脚本,规则未触发;封存 miss 35K、种子 ≤46K) | 66K / 40K | — |

贵的两次 s2(0.112、0.113)的共同点:模型每轮 `write` 一个 3–9K 的 `verify_*.py` 探针脚本,写完即弃,
却每个都作为 base 永久占磁带(封存 miss 78–82K 对 41–45K),这就是 `newFileMinTouches` 的来历。

**第三轮裁决**:

- 通用的、进默认的:`readBasesMinReads: 2`、`newFileMinTouches: 2`、`collapseEdits`、无 patch 时的快照头部、
  摘要不打 `task unknown`。它们只改字节,机制是确定的,历史库核验过。
- 形状相关的:完整基线 + 读指针。1–4 个文件的编码循环上赢(s1 0.050 对 0.068;s2 九次中位 0.085 对 0.120),
  8–12 个文件的工作集上输(s4/s5/s6 六个样本全部高于旧形态,+7% 到 +53%)。机制:工作集整个摆在面前,

## 折叠的适用边界

源代码不折(按扩展名与代码特征密度);grep/glob 结果不折;文件读取按文档折(头尾 + 结构行,
结构块按键新颖性自适应);命令输出按内容判:日志走错误优先。规则细节与借鉴来源见
`docs/fold-content-routing.md`。在编码型多轮场景里折叠基本不发生,收益只在日志/档案型读取
(l1:830K → 46K 字符)。

## 结论

1. **正确性**:slice+折叠 9/9 多轮 + CB20 20/20 完赛 + l1;唯一失败是 l2(需要 stream 的宪法)。
   历史 default 在 s10 上丢事实。折叠没有造成任何一次失败(两次疑似都是 runner 故障或代码折叠,
   后者已用"源代码不折"堵住)。
2. **成本取决于任务形状**:长会话记忆/洪水型便宜 21–37%,链式长任务便宜 80% 以上,检索便宜 11%,
   编码型从 −25% 到 +61%(输出税:每轮重建种子后重新推敲)。
3. **单次运行噪声 ±30%**;评估里能用的对照只有历史数据。要下更强的结论需要每格三次。
